Apply `auth-password-migration.sql` to the existing ChatHttpServer database before deploying this server. The application uses the existing `users.id`, `users.username`, and `users.password` columns. The script creates the table on a new database, and expands an existing password column to VARCHAR(255). Take the normal database backup first; inspect the existing column if it is already wider than 255 characters and retain that larger capacity instead of narrowing it. Existing usernames must have a unique index for registration uniqueness.

New registrations store `pbkdf2_sha256$600000$<16-byte hex salt>$<32-byte hex derived key>` using OpenSSL PBKDF2-HMAC-SHA256 and a fresh cryptographic salt. This format is 118 characters. Login reads the encoded credential by a bound username and verifies it in the application with a constant-time key comparison. Credentials never appear in application SQL text or authentication logs.

Existing plaintext credentials remain readable during transition. Only a successful exact, case-sensitive legacy password comparison triggers an upgrade. The update binds the hash, user id, and previously verified credential, and uses `BINARY password = ?` to avoid overwriting a concurrent change. An unsuccessful migration fails that login; it must never claim a successful upgrade. New credentials are never written as plaintext. The `pbkdf2_sha256$` prefix is reserved for encoded credentials; existing plaintext passwords beginning with that prefix require a password reset before this rollout.

Do not roll back to the old plaintext-only server after credentials have been upgraded. A normal successful login upgrades only that account, so inactive legacy rows remain plaintext until their next successful login or an explicit password reset. Remove the transitional verifier only after all legacy rows are migrated. No production database was modified by this change; the SQL is a deployment step.
